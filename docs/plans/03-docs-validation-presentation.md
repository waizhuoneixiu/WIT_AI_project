## 一、你负责把什么做出来

让团队的产品范围、知识依据、实验结果和参赛表达保持一致，并组织验收。你不仅制作PPT，还负责需求与接口文档、质检知识条目、报告内容模板、对照实验和演示材料。模型与服务代码由队员一实现，App由队员二实现，三人共同完成测试。

## 二、按顺序完成的任务

### 1. 需求和范围确认

- 将总计划整理为首轮功能清单：输入图片与批次、魔搭YOLO26n六类检测、完整框编辑、证据问答、复检建议、人工确认、历史与Markdown报告。
- 访谈3—5名适合的从业者、实验室教师或相关人员，记录角色、现有流程、复核依据和使用困难；如未完成访谈，明确标记需求待验证。
- 区分工业钢带原型、NEU测试集演示和实际工位试用，避免材料写成任意工业零件通用产品。
- 每项功能注明“计划、开发中、已实现、已验证”，由实现者提供证据后更新状态。
- 核对最新赛事通知、学校内部截止、提交格式、篇幅、视频和AI辅助披露要求；以核对结果调整内部安排，不只沿用旧计划日期。

### 2. 知识条目与报告模板

- 首轮准备约20—30条经教师或相关业务人员审核的知识，包括六类缺陷定义、易混淆项、复拍要求、复检步骤与待补信息。
- 每条知识包含id、标题、内容、适用类别、来源、版本、审核状态。先形成队员一可读取的JSON或表格，字段共同确认后冻结。
- 无企业验收标准时，使用“演示规则”标识。一般形成原因作为参考知识，不写成当前钢材的确定工艺根因。
- 报告模板包括批次与图片编号、模型版本、原始预测、有效人工框/备注、review_version、知识引用、建议措施、待补信息及分析来源/过时状态。
- 建立固定复检模板，作为不使用大模型时的对照方案和API不可用时的明确降级展示。

### 3. 维护需求、接口与部署文档

拟维护以下docs内容，文件名可按实际工程调整：

| 文档 | 必须包含的内容 |
|---|---|
| 需求与范围 | 使用者、场景、首轮清单、扩展项、实际实现状态 |
| 接口约定 | 请求/响应、类别与坐标、同步HTTP、复核差异/版本、错误及恢复方法 |
| 数据与模型说明 | 数据来源、划分、版本、真实模型指标与局限 |
| 知识与报告规范 | 条目结构、来源、审核状态、报告字段与引用规则 |
| 安装与部署 | App安装、后端启动、连接、依赖、部署位置及已测环境 |
| 测试与证据 | 用例、设备、版本、真实结果、缺陷与复测记录 |
| 来源清单 | 实际复用仓库、版本、模块、许可、权重与数据来源 |

技术字段由队员一提供并经队员二确认，你负责把说明和合成样例维护一致，不自行猜测服务已支持的功能。账号、密钥、聊天截图和私人联系方式不放入公共材料。

### 4. 组织验收和价值实验

模型精度由队员一运行和出具原始记录，你核对数据划分、统计口径与结果表是否匹配。界面流程由队员二提供安装包，你组织其他成员交叉操作，记录失败步骤。

至少覆盖以下用例：

- 原始测试图片的正常上传、单框与多框展示。
- 未检出目标缺陷、图像不可用、错误文件与重复点击。
- 人工新增/改类/移动/缩放/删除框、版本冲突、重启恢复与报告版本。
- 问答引用是否存在、事实是否对应当前图片、缺知识时是否说明不足。
- 同步HTTP等待/失败、重复点击、未知上传结果和已保存记录恢复。
- 魔搭不可达时检测失败；业务API可达时仍可查询已存记录，不承诺离线检测。
- 批次图片数、原模型框数与已确认图片数口径一致，per_class不冒充人工确认类别统计。

围绕大模型价值，优先比较“检测+固定复检模板”和“检测+大模型+知识检索”，使用相同检测证据和难度接近的任务，交叉安排顺序。记录完成时间、人工修改次数、事实一致性、知识引用正确性及API成本。无行业专家时，将结果称为初步可用性测试。

已有YOLO26n离线指标以模型卡和原始记录为准；本轮分别测魔搭推理、业务请求和App总等待时延，不能套用本地P95。流程时间改善约30%仍是待验证目标，未达目标也保留真实结果。

### 5. 计划书、PPT与演示材料

- 根据真实进展更新计划书，不把拟做功能写成现有功能。
- 组织答辩内容：业务问题、应用场景、系统流程、模型与数据、App演示、对照实验、创新与限制、后续应用。
- 以“YOLO检测—知识辅助复检—人工确认—报告追溯”为主线，说明大模型相较固定模板带来的可测收益。
- 准备正式演示脚本、原始测试图片、App截图、视频与离线备用素材。备用素材清楚标注录制或历史结果。
- 预备答疑：为什么选NEU、为什么用YOLO26n、为什么需要大模型、是否能判合格、云检测与本机业务API的区别、与已有项目有何不同、代码如何复用、数据能否支持现场推广。
- 赛事表单、封面、PPT或文件元数据需要作者/署名时，先向用户确认填写内容；本任务书不指定作者，也不从聊天昵称推断姓名。

## 四、你必须交出的文件与证据

- docs目录的需求、接口、数据、部署、测试与来源说明。
- 结构化知识条目、审核与来源记录、报告和固定复检模板。
- 访谈记录或需求待验证说明，不虚构合作企业与用户评价。
- 模型结果汇总和流程对照实验表，能追溯到队员一的原始记录。

## 五、与其他两名队员的交接

交给队员一：结构化知识、已审核引用、固定模板、报告字段与测试用例；从队员一接收模型与服务真实结果、配置、接口变更、费用和限制。

交给队员二：页面文案、状态说明、报告结构、演示路径；从队员二接收安装包、真实截图、构建步骤、支持设备和已知问题。

提交前由三人逐项核对：材料声称的功能是否可运行、性能是否实测、画面是否真实调用、实际部署位置是否说明、实验与测试记录是否对应冻结版本。

## 六、完成标准

- [ ] 另外两名队员能按文档启动、连接并操作完整流程。
- [ ] 知识条目可被后端读取，引用有来源与版本，演示规则有标记。
- [ ] 所有指标区分目标与结果，未虚构合格率、工艺原因和客户收益。
- [ ] 测试记录包含失败与修复，不只有功能截图。
- [ ] PPT和演示围绕产品工作流程，能够说明大模型的实际价值。
- [ ] 正式材料、软件版本、模型版本和演示画面保持一致。
- [ ] 需要作者与署名时已获得明确答复，公共材料不含密钥与私人信息。

## 七、遇到工期压力时的取舍

先保证准确的需求、20条左右核心知识、可执行的报告模板、一轮基础验收与A/C对照，再打磨排版和扩大调研。PPT先写清证据与演示，再做视觉；语音、多模态、复杂市场预测和未验证的收益不作为首轮重点。
