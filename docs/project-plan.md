# 钢见——基于YOLO与大模型协同的钢材表面缺陷质检助手

第二届全国人工智能应用创新大赛项目计划书（NEU·YOLO·KMP修订版）

拟申报：通用赛道·制造领域·本科生组

日期：2026年10月30日

> 本稿依据团队讨论调整为YOLO检测、KMP应用和独立后端的协同方案。按3名本科生、已有电脑、尚无企业合作数据设计。文中的性能、经费和用户收益是拟验证目标，不代表已经实现或完成测试。

## 一、项目摘要

本项目拟开发一款面向钢材表面缺陷检查的辅助质检产品，采用“轻量YOLO检测模型+云端大模型API+KMP跨平台应用”的架构。以东北大学NEU-DET数据集为训练与验证基础，YOLO识别六类目标缺陷，给出类别、位置框和模型分数；大模型结合检测结果、经审核的知识条目及用户补充信息，生成缺陷解释、复检建议和可追溯报告。

应用端负责拍照或选图、批次信息、检测结果展示、交互问答、人工复核和历史记录；独立后端统一调用YOLO服务与大模型API，并通过WebSocket推送处理进度与报告内容。YOLO可部署在本地工位电脑，魔搭托管作为可选演示部署方式，两种方式保持同一套结果结构。首轮优先交付Android应用，KMP共享代码为后续桌面端保留复用条件。

项目第一阶段交付基于公开数据的可运行原型，验证检测、复检和报告流程。后续再获取同类钢材的真实工位图片及正常样本，评估现场误报、跨批次泛化和实际使用收益。应用定位先聚焦热轧钢带表面，不将NEU测试结果泛化为任意工业零件的检测能力。

核心价值主张：YOLO负责“找出缺陷”，大模型负责“解释结果、组织复检和报告”，App将检测与人工处置连接起来。小模型与大模型通过数据和工具调用协同，无须联合训练或将两套权重融合。

## 二、赛事定位与参赛目标

拟参加通用赛道制造领域本科生组，通过“检测—查询知识—生成复检清单—人工确认—归档报告”展示可验证的智能体工具调用。创新重点为完整的辅助质检流程和可追溯的人机协作，而非仅展示检测框或调用聊天接口。

截至2026年10月30日，官网显示报名及作品上传截止为11月10日24:00，校赛11月11—20日，区域赛11月21日—12月11日，全国总决赛12月25—27日。按官网及本校实际要求执行，并提前完成首次提交；不假定后续阶段可以随意覆盖已交材料。[1]

首轮目标是范围清楚、流程可运行、实验可复现。尚未完成真实工位试用前，成果应表述为“钢材表面缺陷辅助质检原型”，不宣称已满足工业高速生产线要求。

## 三、需求与应用场景

目标使用者为钢材质检操作人员、质量工程师以及相关教学实验人员。拟解决三类问题：缺陷定位与记录依赖人工；检测模型输出难以转化为可执行复检步骤；批次结果与报告需要重复整理。

上述痛点需通过3—5名实际从业者、实验室教师或相关人员访谈确认，记录检查流程、判定依据、每件操作时间和复核方式。未访谈前不虚构客户需求、合作企业或节省比例。

第一阶段支持App选图、拍照上传、批次检测和测试集顺序回放。现场精度验收以原始测试图片为主；拍照入口可演示采集和上传流程，但拍摄屏幕或打印图片的识别效果不能代替真实钢材工位验证。

典型使用场景：质检员选择批次、上传钢材表面图片，App收到YOLO结果后显示缺陷框；用户点击“生成复检建议”，助手结合知识条目列出需要核查的位置和动作；质检员补充观察、确认结果，系统生成带证据编号的报告。质量负责人可查询该批次已确认的缺陷分布与处置情况。

## 四、数据集与任务定义

### 4.1 使用NEU-DET检测版

官方区分用于分类的NEU-CLS和包含类别、位置标注的NEU-DET。本产品需要定位缺陷，因此选用NEU-DET。NEU官方介绍为1800张200×200像素灰度图、六类各300张，场景为热轧钢带表面。[2]

| 英文标签 | 中文显示名称 |
|---|---|
| crazing | 龟裂 / 网状裂纹 |
| inclusion | 夹杂 |
| patches | 斑块 |
| pitted_surface | 麻点表面 |
| rolled-in_scale | 轧入氧化皮 |
| scratches | 划痕 |

实施时从官方入口获取检测版，核对实际文件数量、图像尺寸、类别和边界框格式，记录下载来源与文件摘要。不将第三方整理包的划分、框数量或许可描述直接当作官方结论。

### 4.2 数据划分

拟按类别分层，以70%训练、15%验证、15%测试作为项目自定划分：在完整1800张且无需排除文件的前提下，为1260、270、270张，每类分别210、45、45张。它不是声称官方统一划分；实际去重和分组后数量变化须如实记录。

训练前检查重复及近重复图片；若有原始实物、母图或采集批次信息，按来源分组，避免相近切片跨集合。若缺少来源信息，保留近重复检查记录，并说明无法完全排除原始采集相关性的局限。增强仅用于训练集；阈值、训练轮数和模型选择使用验证集，冻结测试集只用于最终评价。

### 4.3 数据能支持的结论

NEU提供六类缺陷样本，不能仅凭其充分证明正常钢材上的误报率，也不覆盖所有实际缺陷。没有检出框时显示“未检出六类目标缺陷”，不直接显示“合格”；模型分数不等于产品合格概率。

边界框用于粗定位，不能当作像素级缺陷轮廓或实际缺陷面积。原始图片缺少本项目所需的成像标定和产品验收规则，第一阶段不输出毫米级尺寸、强度结论、自动判废等级或确定的工艺根因。

## 五、产品功能

| 模块 | 第一阶段功能 |
|---|---|
| App检测入口 | 拍照/相册选图、输入批次号和工件编号、查看处理进度 |
| 结果与复核 | 原图/标注图切换、六类缺陷卡片、确认或修正、补充漏检 |
| AI质检助手 | 缺陷解释、工业知识问答、复检清单、基于当前记录的追问 |
| 批次看板 | 检测图片数、待复核数量、已确认缺陷分布、报告入口 |
| 诊断与报告 | 区分检测事实、参考知识和待验证原因；确认后导出报告 |
| 历史与反馈 | 按批次/类别/时间筛选，保存修改与处置记录、审核案例入库 |
| 服务设置 | 后端连接状态、检测与大模型版本、上传提示与超时处理 |

单张图片可能有多个框。看板区分“图片数”“预测框数”和“确认缺陷数”；数据集回放不作为生产抽样，不据此计算真实产线不良率。

使用流程：导入图片与批次信息→本地检测→显示目标缺陷与待复核项→按需生成解释→人工确认→导出报告→审核后加入案例库。

### 5.1 App页面与操作设计

采用“检测、记录、助手、我的”四个主要入口。视觉上以浅灰背景、深色文字和蓝色操作按钮为主，橙色表示待复核，红色表示已确认异常；状态同时提供文字和图标。结果页优先显示原图、缺陷位置与下一步动作，不把模型参数作为主要操作内容。

| 页面 | 主要内容 | 用户可完成的动作 |
|---|---|---|
| 检测页 | 当前批次、图片选择、连接状态、检测按钮 | 拍照、选图、输入批次信息、提交检测 |
| 结果详情页 | 缺陷框、类别与分数、图像质量、复核状态 | 放大区域、确认/修正、请求复检建议 |
| 助手页 | 当前图片或批次上下文、问题输入、引用依据 | 询问缺陷含义、复检方法、批次差异 |
| 记录与批次页 | 历史列表、类别分布、待处理项、报告 | 筛选、查看修改历史、导出已确认报告 |
| 我的与设置页 | 服务连接、版本、上传说明 | 检查连接、查看数据保存位置和服务状态 |

报告使用“AI辅助质检报告”名称，内容包含批次与图片编号、模型检出、人工确认、知识依据、建议措施与待补信息。“原因分析”显示为参考假设；严重程度或合格结论须有实际验收规则与人工确认支持。

### 5.2 功能优先级

首轮必须完成：选图/拍照入口、批次号、YOLO检测、结果框、基于证据的问答、复检建议、人工复核、记录与报告导出。区域赛准备期再评估批次对比和简易处置单；语音输入、语音播报、多模态联合分析、完整工单系统列为扩展。

语音输入和播报属于交互能力，不能单独当作新的质检算法创新。设备故障分析需要设备日志、参数和维修记录，第一阶段仅提供一般知识问答，不从NEU外观图片确定设备故障。

## 六、技术架构与模型分工

```text
KMP App：拍照/选图、批次信息、结果展示、质检问答
             ↓ HTTP上传/查询；WebSocket进度与消息
独立后端：任务管理、权限检查、数据记录、模型调用
       ├─ YOLO推理服务 → 类别、框、分数、模型版本
       │  本地工位部署 / 可选远程托管
       ├─ 已审核知识条目与历史记录检索
       └─ 云端大模型API → 解释、复检清单、报告草稿
             ↓ WebSocket推送；断线后查询恢复
KMP App：人工确认 → 后端归档 → 报告与审核案例
```

### 6.1 轻量YOLO：监督目标检测

NEU-DET已有类别和框标注，因此主线使用监督目标检测，而非只用正常图片训练的异常检测。这里的“小模型”指轻量视觉检测模型，无须额外在本地部署聊天大模型。

结合团队讨论，主线改用Ultralytics YOLO，建议以YOLOv8n为轻量基线、YOLOv8s为同系列对照；若模型负责人已有训练方案，可在首轮实验前统一冻结版本。复用官方训练、预测和结果解析流程，完成NEU六类微调。YOLOv8官方提供上述检测型号与训练、验证、推理能力。[3][4]

核对原始检测标注后转换为所选YOLO格式，明确六类编号、坐标归一化与图像对应关系。灰度图按预训练输入要求做确定性通道转换；比较320与640输入时，注明放大不会产生新的原始细节。模型训练使用GPU更合适，本地推理是否可以使用CPU由目标电脑实测决定。

训练后用验证集选择权重并保留best.pt、类别映射、训练配置和版本信息。best.pt由YOLO运行环境加载执行推理；它不是可以直接交给大语言模型执行的文件。后端只将YOLO输出的结构化证据交给大模型，按需再附局部图片。[5]

首轮不同时引入注意力模块、蒸馏、剪枝和量化。若细长裂纹等类别表现不足，只选择一个明确改动，例如输入分辨率或针对性的训练增强，并进行同条件对照。增强必须同步变换边界框，避免裁剪造成错误标签。

### 6.2 云端大模型：解释与工作流辅助

通过API接入一个支持中文与结构化输出的大模型，优先使用团队可用且来源、费用与数据条款可核对的服务。供应商和具体版本在开发前登记，密钥由后端配置管理。输入包括类别、框、分数、图片编号、用户补充信息和知识片段；只有选用支持图像的模型并取得授权时，才发送局部图片。

大模型负责：解释缺陷术语；依据编号知识条目组织复检步骤；回答与当前检测记录有关的问题；汇总人工确认后的批次结果。若不传图，明确其只解释结构化结果，不宣称其独立进行了视觉复核。

大模型不得直接覆盖本地检测结果或训练标签，不自动批准放行。类别不确定、证据不足或知识缺失时返回需要人工复核。可能原因只能作为待验证线索，不能把知识库中一般原因说成本件产品的确定原因。

低置信度、图片模糊或没有检出目标缺陷时，优先重拍或人工复核。可以实验性请求视觉大模型给出补充观察，但不把“小模型没检出就交给大模型”当作保证补漏的机制。高分预测仍可能出错，需抽样复核。

### 6.3 智能体与知识库

初期建立约20—30条经过教师或业务人员审核的知识条目，内容包括六类缺陷定义、易混淆项、复拍要求和复检步骤；记录来源、版本及适用范围。无实际企业规则时标明“演示规则”，不冒充国家标准或客户验收标准。

智能体可使用读取检测结果、检索知识、生成复检清单、生成报告草稿等受限工具。以日志展示调用顺序、输入证据编号、引用条目和结果。最初可用结构化检索，不为展示概念而强行建设复杂向量数据库。

自然语言批次查询先由后端计算真实统计，再交给大模型组织回答。例如“这个批次哪类缺陷最多”应引用已确认记录；“与上一批相比有什么变化”需具备两批真实记录。未提供生产线、设备或工艺数据时，助手不能编造关联。

案例入库和规则修改需人工审核。用户图片中的文字或检索到的文本不能扩大工具权限，API密钥不进入前端、日志或提交仓库。

### 6.4 KMP前端与独立后端

前端采用Kotlin Multiplatform与Compose Multiplatform组织共享业务逻辑和界面，先交付Android App；相机、文件选择、权限与导出采用平台适配。桌面端是否同时交付取决于首轮进度，iOS不列为必交。[6]

后端拟采用Python、FastAPI、Ultralytics和SQLite，统一封装YOLO推理、大模型调用、记录与报告。文件上传、历史查询和导出采用HTTP接口，检测进度与流式回答采用WebSocket。前端不直接连接大模型供应商，也不内置云端API密钥。[7]

WebSocket消息统一包含任务编号、消息编号、事件类型和数据内容。事件至少覆盖已接收、检测完成、分析片段、分析完成和错误；断线后按任务编号重新查询状态，重复事件不重复创建检测记录。历史或演示报告必须标明状态，不冒充当前实时API响应。

### 6.5 部署与断网行为

本地工位模式：YOLO与业务后端在电脑运行，App通过局域网访问，外部网络中断后仍可检测和保存，大模型解释稍后补生成；App与电脑的局域网连接仍需可用。这里的本地检测指工位电脑检测，首轮不承诺在手机内部离线运行YOLO。

远程演示模式：可将YOLO部署到魔搭创空间等服务，再由业务后端调用。是否支持所需运行环境、资源、鉴权及稳定接口，须在实际平台验证；上传best.pt后还需准备推理程序、依赖和接口封装，不能将上传权重等同于已完成部署。托管模式须注明推理在远程执行；断网时App只能查看缓存和暂存待上传任务。

两种模式使用统一推理接口，避免前端跟随部署变化重写。实际部署地址和访问凭据通过开发配置管理，公开材料仅提供接口结构与合成示例。

### 6.6 模块边界与接口交接

本仓库已设置三个顶层目录，模型、服务和应用功能按本计划实施：

```text
WIT_AI_project/
├─ frontend/    KMP App、共享模型、平台适配与界面
├─ backend/     YOLO推理、大模型编排、接口、记录与报告
└─ docs/        需求、接口、部署、数据、实验与答辩材料
```

先确定以下接口契约，再并行开发。表内为拟定设计，不代表已经存在的服务：

| 接口 | 用途与关键内容 |
|---|---|
| POST /api/inspections | 上传图片与批次信息，返回检测任务编号 |
| GET /api/inspections/{id} | 查询状态、图像尺寸、检测框、模型版本与错误信息 |
| POST /api/inspections/{id}/analysis | 根据指定检测结果生成分析草稿，支持结果版本关联 |
| WS /ws/tasks/{task_id} | 推送处理进度、检测结果和大模型回答片段 |
| POST /api/inspections/{id}/review | 保存人工修正、原因和复核记录版本 |
| GET /api/batches/{id}/summary | 返回真实记录计算的批次统计 |
| GET /api/reports/{id} | 查询或导出报告及其确认状态 |

YOLO输出至少包括记录编号、图片尺寸、类别编号与名称、置信分数、原图坐标系边界框、模型版本和耗时。大模型输出至少区分已知事实、引用知识、参考原因、复检步骤和待补信息；人工修正不覆盖原始预测。

docs中维护前后端均可使用的合成接口样例和错误码，先完成一个样例联调，再替换为实际模型结果。接口须限制图片大小与类型，检查任务访问权限，API密钥保存在服务端。

## 七、实验设计与验收指标

### 7.1 检测实验

在相同划分和评价代码下比较轻量基线、较大配置、至多一个针对性改动。记录预训练来源、输入大小、训练配置与随机种子；资源允许时使用3个训练种子，分别报告结果和均值波动。

| 项目 | 计划口径与目标 |
|---|---|
| 核心精度 | 报告mAP@0.5、mAP@0.5:0.95及六类AP；mAP@0.5初步争取≥0.75 |
| 检测错误 | 固定验证集选定的分数阈值，按IoU=0.5和一对一匹配报告P/R、漏检及误检 |
| 分类混淆 | 展示各类样本数、混淆情况与典型失败图片，不只报平均分 |
| 本地速度 | 指定电脑、batch=1、固定输入分辨率，预热后处理时延P95争取≤500毫秒 |
| 资源占用 | 模型文件大小、参数量、峰值内存；同时说明是否使用GPU |
| 稳定性 | 工位模式断外网且局域网正常时仍可检测和保存；托管模式明确提示离线与待上传状态 |

以上均为拟验证目标，未达目标时如实记录并分析。计时区分预处理、推理和后处理；界面、磁盘及网络开销分别说明。原始数据图像低分辨率下的测试结果不等于真实相机或高速生产线节拍。

### 7.2 大模型价值实验

固定同一套本地检测结果，比较：A.检测结果+固定复检模板；B.检测结果+大模型；C.检测结果+大模型+已审核知识检索。若时间紧，先完成A与C，不强行扩大实验。

评价复检清单是否可执行、事实与检测结果是否一致、知识引用是否准确，以及完成报告所需时间、人工修改次数、响应延迟和API费用。让参与者交叉使用方案、采用难度接近的不同样本；记录参与者背景及样本量。无行业专家时，只能声称初步可用性测试，不能替代专业质检验收。

效率目标为相较固定模板方案，复核与报告总耗时下降约30%，需以实际测试决定是否成立。不得以叙述更流畅代替正确性，也不预设调用大模型必然提高检测mAP。

## 八、应用创新点

1. **检测结果转化为复检动作：**将类别、位置和证据编号与复检清单、人工结论关联，减少模型输出与实际操作之间的断层。
2. **按需使用云端能力：**检测保留在本地，对解释与报告按需调用API，记录实际成本和延迟。
3. **有依据的质检助手：**建议关联经审核知识条目，支持“依据是什么”的追问与回溯。
4. **可验证的人机协作：**保存模型输出、人工修改及建议处置状态，案例经审核后才能用于后续训练。

可重点演示一个可追溯案例：YOLO检出划痕→用户追问依据→助手检索对应知识→用户补充现场观察→助手更新复检建议→质检员确认并记录处置。以是否完成任务、依据是否正确和操作耗时评价协作价值。

NEU检测任务已有大量研究，使用现成数据、训练轻量模型或增加聊天框本身不足以支撑创新。项目应通过工具调用演示、流程对照和可追溯记录证明应用价值，不声称提出全新算法。

## 十一、应用推广与商业验证

先寻找钢材相关实验室或小型加工场所，验证检测与复检记录是否有用，再开展真实同域样本适配。可能的后续交付为本地工位软件、产品适配与部署维护，但定价需通过访谈与试用确认。

获得现场样本后，应补充正常表面、未知缺陷、成像变化及不同批次测试，依据真实验收规则重定阈值。普通手机拍到的任意金属件与NEU钢带图片存在域差异，不能将其简单混合作为现场可靠性证明。

客户数、合作案例、成本收益与收入均须有实际依据；没有企业资源时，保持公开数据原型的成果定位。实际节省按操作时间与用户真实人工成本核算，不虚构漏检损失或市场份额。

## 十二、主要风险与应对

| 风险 | 应对 |
|---|---|
| 数据小、相似样本泄漏 | 去重、可获得来源分组、冻结划分，记录残留局限 |
| 缺少正常件和未知类 | 不输出自动合格；后续补同域正常样本，单独验证误报与拒识 |
| 相近缺陷易混淆 | 报告各类AP与混淆，保留人工复核和失败样例 |
| 大模型编造原因或标准 | 约束证据与知识引用，标注演示规则，允许无法判断 |
| 只做了公开数据演示 | 明确原型边界，争取实际用户反馈与同域小规模验证 |
| API费用或网络不稳定 | 按需调用、限额、缓存与断线恢复；分别验证工位模式和托管模式 |
| 只上传权重但服务无法调用 | 提前准备推理程序、依赖、鉴权与接口；保留可运行的工位演示方案 |
| KMP多端与语音功能超出工期 | 优先Android和核心图片流程，其他端与语音按进度扩展 |
| 拟推广至任意工业零件 | 先限定热轧钢带；扩展材料和零件前重新采集与验证 |
