## 一、项目摘要

本项目拟开发一款面向钢材表面缺陷检查的辅助质检产品，采用“轻量YOLO检测模型+云端大模型API+KMP跨平台应用”的架构。以东北大学NEU-DET数据集为训练与验证基础，YOLO识别六类目标缺陷，给出类别、位置框和模型分数；大模型结合检测结果、经审核的知识条目及用户补充信息，生成缺陷解释、复检建议和可追溯报告。

应用端负责选图/拍照、批次信息、检测框编辑、交互问答、人工复核和历史记录；本机轻量FastAPI/SQLite业务层通过同步HTTP调用已部署的魔搭YOLO26n云服务，并调用DeepSeek生成辅助建议。首轮交付KMP Android应用，不在本机安装模型库，报告固定为Markdown。

项目第一阶段交付基于公开数据的可运行原型，验证检测、复检和报告流程。后续再获取同类钢材的真实工位图片及正常样本，评估现场误报、跨批次泛化和实际使用收益。应用定位先聚焦热轧钢带表面，不将NEU测试结果泛化为任意工业零件的检测能力。

核心价值主张：YOLO负责“找出缺陷”，大模型负责“解释结果、组织复检和报告”，App将检测与人工处置连接起来。小模型与大模型通过数据和工具调用协同，无须联合训练或将两套权重融合。

## 二、赛事定位与参赛目标

拟参加通用赛道制造领域本科生组，通过“检测—查询知识—生成复检清单—人工确认—归档报告”展示可验证的智能体工具调用。创新重点为完整的辅助质检流程和可追溯的人机协作，而非仅展示检测框或调用聊天接口。

截至2026年10月30日，官网显示报名及作品上传截止为11月10日24:00，校赛11月11—20日，区域赛11月21日—12月11日，全国总决赛12月25—27日。按官网及本校实际要求执行，并提前完成首次提交；不假定后续阶段可以随意覆盖已交材料。[1]

首轮目标是范围清楚、流程可运行、实验可复现。尚未完成真实工位试用前，成果应表述为“钢材表面缺陷辅助质检原型”，不宣称已满足工业高速生产线要求。

## 三、需求与应用场景

目标使用者为钢材质检操作人员、质量工程师以及相关教学实验人员。拟解决三类问题：缺陷定位与记录依赖人工；检测模型输出难以转化为可执行复检步骤；批次结果与报告需要重复整理。

上述痛点需通过3—5名实际从业者、实验室教师或相关人员访谈确认，记录检查流程、判定依据、每件操作时间和复核方式。未访谈前不虚构客户需求、合作企业或节省比例。

第一阶段支持App选图、拍照上传、按批次归档的单图检测；批量处理和测试集顺序回放留待后续。现场精度验收以原始测试图片为主；拍照入口可演示采集和上传流程，但拍摄屏幕或打印图片的识别效果不能代替真实钢材工位验证。

典型使用场景：质检员选择批次、上传钢材表面图片，App收到YOLO结果后显示缺陷框；用户点击“生成复检建议”，助手结合知识条目列出需要核查的位置和动作；质检员补充观察、确认结果，系统生成带证据编号的报告。质量负责人可查询该批次原模型缺陷分布和图片复核状态，两种统计不混为人工确认后的缺陷数量。

## 四、数据集与任务定义

### 4.1 使用NEU-DET检测版

官方区分用于分类的NEU-CLS和包含类别、位置标注的NEU-DET。本产品需要定位缺陷，因此选用NEU-DET。NEU官方介绍为1800张200×200像素灰度图、六类各300张，场景为热轧钢带表面。[2]

| 英文标签 | 中文显示名称 |
|---|---|
| crazing | 龟裂 / 网状裂纹 |
| inclusion | 夹杂 |
| patches | 斑块 |
| pitted_surface | 麻点表面 |
| rolled-in_scale | 轧入氧化皮 |
| scratches | 划痕 |

实施时从官方入口获取检测版，核对实际文件数量、图像尺寸、类别和边界框格式，记录下载来源与文件摘要。不将第三方整理包的划分、框数量或许可描述直接当作官方结论。

### 4.2 数据划分

拟按类别分层，以70%训练、15%验证、15%测试作为项目自定划分：在完整1800张且无需排除文件的前提下，为1260、270、270张，每类分别210、45、45张。它不是声称官方统一划分；实际去重和分组后数量变化须如实记录。

训练前检查重复及近重复图片；若有原始实物、母图或采集批次信息，按来源分组，避免相近切片跨集合。若缺少来源信息，保留近重复检查记录，并说明无法完全排除原始采集相关性的局限。增强仅用于训练集；阈值、训练轮数和模型选择使用验证集，冻结测试集只用于最终评价。

### 4.3 数据能支持的结论

NEU提供六类缺陷样本，不能仅凭其充分证明正常钢材上的误报率，也不覆盖所有实际缺陷。没有检出框时显示“未检出六类目标缺陷”，不直接显示“合格”；模型分数不等于产品合格概率。

边界框用于粗定位，不能当作像素级缺陷轮廓或实际缺陷面积。原始图片缺少本项目所需的成像标定和产品验收规则，第一阶段不输出毫米级尺寸、强度结论、自动判废等级或确定的工艺根因。

## 五、产品功能

| 模块 | 第一阶段功能 |
|---|---|
| App检测入口 | 拍照/系统选图、输入批次号和可选工件编号、查看等待/成功/失败 |
| 结果与复核 | 原图/标注图切换、六类缺陷卡片、确认或修正、补充漏检 |
| AI质检助手 | 缺陷解释、工业知识问答、复检清单、基于当前记录的追问 |
| 批次看板 | 检测图片数、原模型框与类别分布、图片复核数量、报告入口 |
| 诊断与报告 | 区分原预测、人工结果、参考知识与原因假设；保存/分享Markdown报告 |
| 历史与反馈 | 按批次/类别/复核状态分页筛选，恢复原图、有效框、复核版本与分析 |
| 服务设置 | 后端连接状态、检测与大模型版本、上传提示与超时处理 |

单张图片可能有多个框。看板区分“图片数”“原模型框数”和“已确认图片数”；per_class仍为原预测类别分布，不能当成人工确认的缺陷统计，也不计算真实产线不良率。

使用流程：导入图片与批次信息→业务API调用魔搭云检测→显示原预测→完整框编辑与人工复核→按需生成解释/问答→归档并导出Markdown。

### 5.1 App页面与操作设计

采用“检测、记录、助手、我的”四个入口，结果详情由检测和记录进入。UI编写前读取Aboard设计参考，使用浅色纸张感、柔和粉彩卡片与圆角操作；状态同时提供文字，不能只靠颜色。结果页优先显示原图、缺陷位置与复核操作，不把模型参数作为主要操作内容。

| 页面 | 主要内容 | 用户可完成的动作 |
|---|---|---|
| 检测页 | 当前批次、图片选择、连接状态、检测按钮 | 拍照、选图、输入批次信息、提交检测 |
| 结果详情页 | 缺陷框、类别与分数、图像质量、复核状态 | 放大区域、新增/改类/移动/缩放/删除框、确认、请求复检建议 |
| 助手页 | 当前图片或批次上下文、问题输入、引用依据 | 询问缺陷含义、复检方法、批次差异 |
| 记录与批次页 | 历史列表、类别分布、待处理项、报告 | 筛选、恢复最新复核、导出对应版本Markdown报告 |
| 我的与设置页 | 服务连接、版本、上传说明 | 检查连接、查看数据保存位置和服务状态 |

报告使用“AI辅助质检报告”名称，内容包含批次与图片编号、模型检出、人工确认、知识依据、建议措施与待补信息。“原因分析”显示为参考假设；严重程度或合格结论须有实际验收规则与人工确认支持。

### 5.2 功能优先级

首轮必须完成：选图/拍照入口、批次号、YOLO检测、结果框、基于证据的问答、复检建议、人工复核、记录与报告导出。区域赛准备期再评估批次对比和简易处置单；语音输入、语音播报、多模态联合分析、完整工单系统列为扩展。

语音输入和播报属于交互能力，不能单独当作新的质检算法创新。设备故障分析需要设备日志、参数和维修记录，第一阶段仅提供一般知识问答，不从NEU外观图片确定设备故障。

## 六、技术架构与模型分工

```text
KMP Android：选图/拍照、批次信息、原图与框编辑、质检问答
             ↓ 同步 HTTP 上传、查询、复核与报告
本机轻量 FastAPI + SQLite：输入校验、云调用、记录与版本
       ├─ 魔搭 Gradio → YOLO26n@640 ONNX → 类别、框、分数
       └─ DeepSeek 云 API → 解释与复检建议；失败则明确规则降级
             ↓ HTTP 完成结果；已知记录可重新查询
KMP Android：人工确认 → 记录归档 → Markdown 保存/分享
```

### 6.1 已有 YOLO26n 模型

实际基线是 YOLO26n@640、Ultralytics 8.4.193，NEU-DET 六类检测；魔搭部署包使用 ONNX Runtime CPU 执行 `best.onnx`。模型训练、划分和离线指标已经有仓库产物，见[模型卡](../backend/docs/模型卡_n640.md)与[训练实验记录](../backend/docs/训练实验记录.md)。本轮沿用该模型，不训练新模型，不在本机安装 YOLO、PyTorch 或 ONNX Runtime。[3][4]

模型训练的原类别顺序与项目对外编号不同，后端已有映射，App统一使用共同契约的编号。框是统一方向后的原图像素坐标；640输入不会增加200×200原始图片的细节，结果不能推导毫米尺寸或合格概率。原预测永久保留，人工新增/改动框另存且没有模型置信度。

后续算法实验须独立冻结数据、阈值和评价配置，不能成为当前前端联调的前置任务。既有离线指标与新的云端时延分别报告。

### 6.2 云端大模型：解释与工作流辅助

已有后端支持 DeepSeek 云 API（默认 deepseek-chat）；本轮只使用云端来源或明确的规则模板降级，不下载本地大模型。前端调用业务 API 的 analysis/chat，不接触供应商令牌。

大模型基于当前记录、有效人工复核结果和参考知识生成 facts、references、hypotheses、recheck_steps、missing_information。未传图时只解释结构化结果，不宣称独立视觉复核；不能编造标准、工艺根因、自动批准放行或覆盖预测。知识来源与审核状态仍需真实核对。

分析关联 review_version，人工复核变化后旧分析标记 stale，报告明确其来源与版本。上下文问答使用 inspection/batch 和明确的ID，统计由后端计算，不能由大模型自行估算。

### 6.3 知识与人工复核

已有后端包含六类规则模板；约20—30条经过教师或业务人员审核的知识仍是内容建设目标，未审核内容不得标为行业依据。知识记录来源、版本、适用范围；无企业标准时明确演示规则，不建设无需求的复杂向量数据库。

首期完整框编辑包括新增、改类、移动、缩放和删除。每次提交相对原预测的完整 add/update/delete 差异，新增框使用 UUID，并附必填 base_version；版本冲突刷新后人工重新确认。原始 detections 不变，reviewed_detections 给出当前有效结果。详细字段和兼容规则只在[共同契约](plans/04-shared-contract.md)维护。

批次 per_class/model_box_count 统计原模型预测，confirmed_count 是已确认/已修正的图片数。人工有效框与原框分别展示，本轮不宣称提供复核后的类别汇总。案例审核入库、完整处置单和训练反馈链留待后续。

### 6.4 KMP Android 与同步业务接口

前端使用 Kotlin Multiplatform 与 Compose Multiplatform；Android 平台负责采集、文件保存和分享。共享数据模型、网络调用和页面状态，桌面/iOS本轮不交付。[6]

**编写 UI 代码前必须读取 [Aboard 设计参考](../frontend/Aboard-design.md)。** 保留浅色纸张感、柔和卡片和圆角主操作，按手机屏幕适配字号、间距与触控目标，不照搬营销网页布局。

本机运行 Python/FastAPI/SQLite 轻量业务层，统一图片方向、输入校验、存储和云调用；不加载本地模型。检测、分析、问答均同步 HTTP 返回最终结果与 task_id。现有 WebSocket 仅回放 accepted/completed，本轮 App 不依赖流式事件、不伪造进度百分比。[7]

详情本轮补齐 original_url、review_version、reviewed_detections 和最新 analysis。历史筛选使用批次/类别/复核状态，total与条件一致；没有时间筛选承诺。报告格式固定 Markdown，包含原预测、当前人工结果和备注、版本、分析来源与过时状态。

### 6.5 云部署与断网行为

已有魔搭云推理部署记录见[魔搭部署记录](../backend/docs/魔搭部署记录.md)。该服务仅提供 Gradio 检测，不承载业务历史、复核、大模型或报告；业务层需要新增云适配，执行 upload → call/detect_ui → SSE 完成结果，再返回现有 `/api` 响应。部署曾验证成功不代表本轮端到端已验收。

Android通过业务 API 地址连接本机服务，模拟器与真机按实际网络配置。魔搭与DeepSeek令牌只保存在后端环境配置，App仅持有必要的业务访问配置。

外网或魔搭不可用时检测失败，不能返回空框假装成功；业务 API 可达时可查已保存记录。没有离线检测和可靠待上传队列承诺。上传响应丢失且无记录编号时不自动重发，提示先查历史或由用户明确重试。

### 6.6 模块与接口交接

`frontend/` 承担 Android、共享模型和 UI；`backend/` 承担轻量 API、云推理适配、持久化、复核和报告；`docs/` 维护路线图、契约和证据。

已有基础接口与本轮新增规则在[共同契约](plans/04-shared-contract.md)分开标注，原始样例见[后端样例](../backend/docs/api_samples/)。代码实现后同步样例和验收状态，不能仅靠文档宣称完成。UI和契约测试可使用明确标记的夹具，真实演示必须走业务API和魔搭调用。

## 七、实验设计与验收指标

### 7.1 检测实验

本轮沿用已有模型实验、划分与评价证据，不重新训练。后续若比较更大配置或一个针对性改动，须在相同划分与评价代码下记录来源、输入、配置和随机种子；多种子结果属于后续实验。

| 项目 | 计划口径与目标 |
|---|---|
| 核心精度 | 报告mAP@0.5、mAP@0.5:0.95及六类AP；mAP@0.5初步争取≥0.75 |
| 检测错误 | 固定验证集选定的分数阈值，按IoU=0.5和一对一匹配报告P/R、漏检及误检 |
| 分类混淆 | 展示各类样本数、混淆情况与典型失败图片，不只报平均分 |
| 时延 | 沿用已有离线基准；本轮另测魔搭推理、上传/排队/网络及Android等待耗时，不套用本地500毫秒目标 |
| 资源占用 | 模型文件大小、参数量、峰值内存；同时说明是否使用GPU |
| 稳定性 | 魔搭或外网不可达时明确失败且不生成成功记录；业务API可达时仍可查询已保存记录 |

以上实验口径中，已有YOLO26n离线结果以模型卡为准；新增云端与App验证仍待执行，未达目标时如实记录并分析。计时区分预处理、推理和后处理；界面、磁盘及网络开销分别说明。原始数据图像低分辨率下的测试结果不等于真实相机或高速生产线节拍。

### 7.2 大模型价值实验

固定同一套检测证据，比较：A.检测结果+固定复检模板；B.检测结果+大模型；C.检测结果+大模型+已审核知识检索。若时间紧，先完成A与C，不强行扩大实验。

评价复检清单是否可执行、事实与检测结果是否一致、知识引用是否准确，以及完成报告所需时间、人工修改次数、响应延迟和API费用。让参与者交叉使用方案、采用难度接近的不同样本；记录参与者背景及样本量。无行业专家时，只能声称初步可用性测试，不能替代专业质检验收。

效率目标为相较固定模板方案，复核与报告总耗时下降约30%，需以实际测试决定是否成立。不得以叙述更流畅代替正确性，也不预设调用大模型必然提高检测mAP。

## 八、应用创新点

1. **检测结果转化为复检动作：**将类别、位置和证据编号与复检清单、人工结论关联，减少模型输出与实际操作之间的断层。
2. **按需使用云端能力：**本机业务层调用魔搭完成检测，按需调用DeepSeek解释，分别记录实际成本和延迟。
3. **有依据的质检助手：**建议关联经审核知识条目，支持“依据是什么”的追问与回溯。
4. **可验证的人机协作：**保存模型输出、人工修改及建议处置状态，案例经审核后才能用于后续训练。

可重点演示一个可追溯案例：YOLO检出划痕→用户追问依据→助手检索对应知识→用户补充现场观察→助手更新复检建议→质检员确认并记录处置。以是否完成任务、依据是否正确和操作耗时评价协作价值。

NEU检测任务已有大量研究，使用现成数据、训练轻量模型或增加聊天框本身不足以支撑创新。项目应通过工具调用演示、流程对照和可追溯记录证明应用价值，不声称提出全新算法。

## 十一、应用推广与商业验证

先寻找钢材相关实验室或小型加工场所，验证检测与复检记录是否有用，再开展真实同域样本适配。可能的后续交付为本地工位软件、产品适配与部署维护，但定价需通过访谈与试用确认。

获得现场样本后，应补充正常表面、未知缺陷、成像变化及不同批次测试，依据真实验收规则重定阈值。普通手机拍到的任意金属件与NEU钢带图片存在域差异，不能将其简单混合作为现场可靠性证明。

客户数、合作案例、成本收益与收入均须有实际依据；没有企业资源时，保持公开数据原型的成果定位。实际节省按操作时间与用户真实人工成本核算，不虚构漏检损失或市场份额。

## 十二、主要风险与应对

| 风险 | 应对 |
|---|---|
| 数据小、相似样本泄漏 | 去重、可获得来源分组、冻结划分，记录残留局限 |
| 缺少正常件和未知类 | 不输出自动合格；后续补同域正常样本，单独验证误报与拒识 |
| 相近缺陷易混淆 | 报告各类AP与混淆，保留人工复核和失败样例 |
| 大模型编造原因或标准 | 约束证据与知识引用，标注演示规则，允许无法判断 |
| 只做了公开数据演示 | 明确原型边界，争取实际用户反馈与同域小规模验证 |
| API费用或网络不稳定 | 按需调用、超时和明确错误；验证魔搭/AI失败及已保存记录恢复 |
| 魔搭可演示但业务API尚未接通 | 先补Gradio云适配并做真实单图验证；保留明确标记的历史演示素材，不安装本地模型兜底 |
| KMP多端与语音功能超出工期 | 优先Android和核心图片流程，其他端与语音按进度扩展 |
| 拟推广至任意工业零件 | 先限定热轧钢带；扩展材料和零件前重新采集与验证 |

建议演示顺序：在App选择一张未参与训练的测试图片并输入批次号→显示实际等待状态与YOLO结果→点击缺陷卡片并追问依据→助手检索知识、生成复检清单→人工确认→查看该批次记录并导出报告。再展示一个混淆或漏检样本，说明人工接管。演示魔搭不可达时的明确错误，以及业务API可达时已保存记录的恢复；不承诺离线检测。

演示使用测试集图片须明确标注；不得将回放称为实时生产线，也不得将AI建议称为真实质检员已确认的结论。

**对外一句话介绍：钢见以YOLO识别钢材表面缺陷，以大模型提供有依据的复检建议，通过App完成从检测、问答到人工确认与报告的可追溯流程。**
